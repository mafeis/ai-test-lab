## 1. 测试目标

回答一个问题：agent 命令行（Hermes）驱动思考档位模型 **Qwen3.8-Flash（reasoning effort=xhigh，最高档）**，能否在**零人工干预**下、仅凭两条自然语言指令，自主完成从 Blender 程序化建模、多轮视觉自检修模，到骨骼绑定、编舞、程序化配乐、渲染合成的完整 3D 动画流程。

本文三个度量口径，先在这里说清：

- **token**：模型输入/输出文本的计量单位，本文用它衡量工作量。
- **消息**：会话内的一条往来记录，本文用它统计会话规模。
- **视觉自检（vision_analyze）**：把渲染图抽取出来回传给模型检查、由模型像人眼一样指出缺陷的工具调用。

## 2. 输入指令

全部用户输入为 3 条有效指令：

```
1. 调用 blender 做一个初音的高精度模型  要穿着清凉的
2. 继续
3. 最终验收 通过 确定是高质量的模型后 做一个跳舞的视频 30s 左右
（收尾追问：这个视频的路径是什么）
```

未提供任何参考图、模型文件或分镜要求，全部由 agent 自主设计。这说明：成片质量完全取决于模型自身的任务拆解与自检能力，指令本身不含任何专业制作知识。

## 3. 执行过程

### 3.1 程序化建模：6 轮渲染验收

1. 按技能流程编写程序化建模脚本：动漫比例人偶、标志性葱绿双马尾、无袖清凉装束，用 Cycles（Blender 的高保真渲染引擎）出图验证。
2. 首次内存溢出（OOM，内存耗尽导致进程被系统终止）：voxel（把网格重建成块状结构时小方块的边长，越小越精细也越耗内存）0.008 的重网格叠加二级细分，使网格膨胀到 258MB，16GB 内存被 SIGKILL 强杀（退出码 137）。AI 随即自主降低网格精度（具体取值见文末参数表）、启用 GPU 加速（Metal）后跑通；网格从 258MB 降到 64MB。这说明：在 16GB 这类受限机器上，「降精度保跑通」比「坚持原参数调不顺」更有效。
3. 逐轮视觉自检并修复：
   - 第 2–3 轮：耳机头带垂在脸前、发圈朝向错误、裙摆棱条刺穿、曝光过强（更换配色方案修正，方案名见文末）。
   - 第 4 轮：中分刘海露额、领带浮空、裙靴间悬空环。
   - 第 5–6 轮：补实心刘海板，精确到眉线不遮眼；最终 **6/6 PASS**（6 轮验收全部通过）。

   6 轮验收全部由 AI「看图—修—重渲」闭环驱动，无人工质检介入，这是本测试成立的关键机制。

### 3.2 舞蹈视频（30 秒）

1. **6 帧预览先行**：先用 6 帧验证骨骼绑定与编排，确认后再上 720 帧全量渲染。这说明：把试错成本压在预览帧上，而不是全片上。
2. 编舞共 8 段，全部与 128 BPM（每分钟节拍数）对齐：弹跳热身 → 波浪手 → 侧滑步摆臂 → 律动指点 → 双跳 → 360° 旋转（马尾离心外摆）→ 葡萄藤步+拍手 → V 字定格。
3. 动作实现：Empty 骨链刚体层级驱动（以空物体作父级控制骨链），双马尾用弹簧物理模拟随动作甩动，全片共 720 帧关键帧（关键帧：在指定时刻钉住姿势，中间由软件补全）。
4. BGM 程序化合成：直接由代码生成波形，不依赖现成乐曲；和弦进行 Am-F-C-G 电子流行，速度 128 BPM 与编舞对齐（响度处理参数见文末）。
5. 渲染：EEVEE（Blender 的实时渲染引擎）输出 720×960 @24fps，约 0.7 秒/帧；ffmpeg 合成 H.264+AAC 成片。

### 3.3 渲染翻车与自愈（3 次）

| 问题 | 自愈方式 |
|---|---|
| 漏设渲染结束帧号（frame_end），默认只渲出 250 帧 | 发现后补渲 251–720 |
| 补渲批次文件名被 `%04d` 模板污染，产生 471 帧脏文件 | 整批废弃，改用 `####` 模板 |
| 场景 `frame_end=250` 再次钳制补渲 | 放弃补丁式修复，720 帧一次性干净重渲 |

3 次翻车均由 AI 自行发现、诊断并修复；且均出在「补渲」环节。这说明：渲染管线一次干净全量重渲，比多次打补丁式补渲更可靠。

## 6. 测试结论

**成功**：两条指令、零人工干预，agent 自主完成建模→修模→绑定→编舞→配乐→渲染合成全流程。

关键经验（对应数字与过程见前文各节，此处不复述）：

1. 视觉自检（vision_analyze）是无人值守质检的核心：没有人工把关时，「看图—修—重渲」闭环可以替代人工验收。
2. 先预览后全量（先看少量预览帧再上全片）能大幅节省试错成本。
3. 资源受限机器上出现 OOM 时，降精度重跑比死磕参数更有效。
4. 渲染管线要一次干净重渲，优于多次补渲：本期的翻车全部来自补渲环节。
5. 同一模型在不同入口下的判断不一致，值得横向测试（见下）。

### 附加发现：同一提示词、不同入口，安全判断不一致

同一提示词走 api_server 入口的另一会话中，模型**直接拒绝**了「清凉」方向（初音官方设定 16 岁），并说明程序化建模达不到「高精度」；desktop 会话则将任务理解为「无袖清凉装束」的风格化人偶并执行成功。这说明：入口通道会影响同一模型的安全判断与任务执行，评估模型能力时不能把不同入口视为等价。
